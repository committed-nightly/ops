# Weekly review — 2026-09-03

First week of data. Everything below is week one — there is no "last week"
and no four-week mean yet. Where the report format calls for those
comparisons, it says "first week" instead of manufacturing a baseline.

The collector ran clean — no Slack scope errors, all five channels read.
One accuracy gap in its own numbers surfaced during review; it's called
out under **No-work nights** and **What the numbers don't show** rather
than patched, since I don't own `scripts/collect-metrics.py` and a
silent hand-correction would be exactly the kind of not-comparable count
this whole process exists to avoid.

## Headline

Three repos shipped this week — `append-only`, `lockstep`, `blamecheck`
— all from Richmond, all the same shape: a small zero-dependency CLI
that shells out to git and exits 0/1/2, where 2 means "the check did not
run." That's not a coincidence of taste; it's the org's house style
hardening. `append-only` in particular went through real review — three
rounds, six blocking-adjacent asks, all substantive — and came out
better for it: Jen found a merge-handling bug that would have made the
tool silently pass on the exact failure it exists to catch. The one
miss this week isn't in the code, it's in the ledger: a no-work night
on 2026-09-01 was reported to `#incidents` but never made it to
`#shift-log`, so the collector's own "no-work nights" count reads 0
when the real number is 1. First week, so nothing to compare it to yet
— but it's worth watching whether that gap recurs.

## What the numbers don't show

**The no-work night wasn't fixed, and Jen said so.** Her closing note
in `#incidents` is explicit: *"resolved, cause unconfirmed... I'd stop
short of calling it fixed. Nothing was done to it, so it can come
back."* The leading theory — App-auth env vars colliding with the
session's egress proxy — is plausible but unconfirmed, and the only
other data point (no transcript link on any shift this week,
`logbook`#6) suggests whatever varies between sessions varies in more
than one place. Worth tracking whether it recurs before anyone calls it
closed.

**Dan force-pushed over a ledger entry this week, and there's nothing
stopping it from happening again.** `flakehunt` — a repo from before
this collection window — was deleted outright rather than archived, and
its `SHIFTS.md` line vanished with it, discovered only because
`append-only` flagged the truncation on its first real run
(`logbook`#4). Dan's answer in the issue: *"we can ignore, that was a
test... wipe it from history using force push."* Richmond then filed
`logbook`#9: `logbook` is a private repo on the free plan, which means
branch protection literally isn't available for it — anyone with write
access, including the shifts themselves, pushes straight to `main`, no
review, no force-push guard. The tool built this week to catch exactly
this kind of silent ledger damage can't be enforced on the one repo
where it matters most, and the gap has already been used once, by the
org's own owner, before the tool existed to flag it.

**The "gates that pass when they shouldn't" pattern isn't just a house
style anymore — this week's three repos are one after another instance
of it.** `append-only` needed three review rounds to close off five
separate ways it could report `clean` on a file it hadn't actually
checked (header overrun, empty `--after` match, a directory path, a
typo'd `--since` target, and — flagged but not fixed — a file deleted
before the range starts). `lockstep` is built around the same worry
(a rule whose glob matches nothing can never fire, silently). Richmond
named it himself, unprompted, in the `blamecheck` shift-log post:
*"Third in what's now clearly a family... checks that git itself won't
do for you."* Noted without judgment, per the brief — but worth
watching whether the org ever builds anything that isn't a gate.

**The shift-log outcome parser is narrower than the actual shift
count.** Only 3 of the 7 substantive posts in `#shift-log` this week
contain one of the exact outcome words the collector matches
(`shipped-for-review`, `merged`, `closed`); the `lockstep` and
`blamecheck` build posts and the third `append-only` review-response
post all logged real work with no parseable outcome. `shifts_logged: 3`
in the series is therefore a lower bound on activity, not a shift
count — worth knowing before reading too much into that column over
time.

## My view

Too early to call a trend — this is one week, and the report format
says so on every line where a comparison would otherwise go. What I can
say: the work itself is good and the review is not decorative. Jen's
reviews read like she actually ran the reproduction steps rather than
trusting the PR description — the `lockstep` approval in particular
describes rebuilding the demo repo from scratch and running all three
"try to break it" cases for real. Richmond's self-correction on the
greedy-embedding claim is the kind of thing that's easy to fake and
hard to fake convincingly; fuzzing it independently rather than taking
Jen's number is a good sign, not a neutral one.

The org's actual weak point this week isn't either of them — it's the
scaffolding around them. Two separate no-trace failures landed in the
same seven days: a no-work night that never reached the ledger, and a
force-pushed repo deletion that also never reached the ledger, on a
repo that structurally cannot be protected from it. Both were caught
by a human or a tool built this week, not by anything standing. That's
the thing worth watching, not the disagreement count.
